# Mini AdTech Engine

<p>Бэкенд-сервис, который подбирает рекламный ролик для просмотра видео, учитывает события (impression/click/просмотр) и корректно списывает деньги с бюджета рекламной кампании.</p>

### Описание реализации, ахитектуры и алгоритмов - [Архитектура и реализация](Implementation.md)

---

## 1. Конфигурация и запуск

### Конфиг `configs/config.toml`

### Запуск локально

1. Поднять Postgres (локально или через docker).
2. если нет пользователя и базы данных выполнить
```sql
CREATE ROLE adengine_user LOGIN PASSWORD 'L$56dgBN109!3';
CREATE DATABASE adengine OWNER adengine_user;
```
3. включить миграцию
```bash
export MIGRATE=1
```
4. запустить сервис
```bash
go run ./cmd/adserver
# или
go build -o adserver ./cmd/adserver && ./adserver
```
5. также можно через make [смотри команды в Makefile:](Makefile)

### Запуск в Docker (docker-compose)
<p>необходимо задать имя сервиса(задан в docker-compose.yml) в переменой host для Postgresql</p>
```toml
[pgstorage]
host = "postgres"
```

6. запустить сервис
```bash
make docker-up
```
7. потушить
```bash
make docker-down
```

## 2. Логирование

- Логгер: `mtlog`, формат CLEF/структурированный JSON.
- Вывод:
  - консоль
  - опционально — файл (конфигурируется через `[logger]`).
- Логируются:
  - старт/остановка сервера,
  - ошибки БД / HTTP,
  - ключевые бизнес-операции (request, click, view, billing).

Для продакшена логично добавить:

- Prometheus-метрики (RPS, latency, ошибки, биллинг),
- кореляционный `request_id`,
- trace-ID для распределённого трейсинга.

## 4. Возможное развитие до продакшена

- Вынести скоринг/подбор в отдельный сервис (in-memory index + event sourcing).
- Freq cap + лимиты перенести в Redis / Redis Cluster.
- Добавить Kafka/NATS для событий (`impression/click/view/spend`).
- Перевести статистику на ClickHouse/OLAP.
- Внутренний API перевести на gRPC.
- Расширить таргетинг (интерфейсы, сегменты, демография).
- Добавить полноценный A/B-тестинг, фрод-детект, оптимизацию по конверсиям и т.п.

## 5. Ответы на вопросы по заданию

1. Сталкивался ли ранее с задачами AdTech?

C готовыми RTB-платформами и OpenRTB в проде не работал, но подход знаком по чтению публичной документации SSP/DSP и примерам аукционов (Vickrey, second price, real-time bidding). Здесь реализован упрощённый аукцион-поиск без внешних протоколов, опирающийся на собственный скоринг и таргетинг.

2. В чём основная сложность такого сервиса?

Конкурентный и честный биллинг: при больших RPS не допустить двойного списания и гонок по бюджетам.

Масштабируемый поиск и ранжирование, когда кампаний и таргетов много.

Идемпотентность и консистентность событий (impression/click/view) под ретраями и сетевыми ошибками.

Разделение горячего on-line пути (latency < 10–50 ms) и тяжёлой аналитики.

3. В чём лично для меня была самая большая сложность?

- Сбалансировать простоту дизайна (для тестового) с правильным биллингом:
- аккуратно привести CPM/CPC к единому алгоритму списаний;
- разрулить идемпотентность кликов и показов;
- сделать схему, которая позволит потом расширить биллинг через spend_events без ломки API.

4. Как масштабировать на 10k / 100k / 1M RPS?

10k RPS:
- Один-несколько инстансов Go-сервиса под Kubernetes/VM.
- Postgres с нормальной конфигурацией, индексами.
- Кеширование реже меняющихся данных (таргетинг кампаний) в памяти/Redis.

100k RPS:
- Sharding по campaign_id или user_id (несколько Postgres/кластер).
- Кеш таргетинга в памяти процесса + периодическая синхронизация.
- Вынесение событий (impression/click/view) в очередь (Kafka/NATS) с асинхронным биллингом (но с ACID-путём для критических штук).
- Строгие лимиты по соединениям к БД, пулы, read-replicas для статистики.

1M RPS:
- Полноценная разделённая архитектура: on-line путь (скоринг/таргетинг) и offline/near-real-time биллинг/стата.
- Возможно, переход с Postgres на специализированное KV/OLAP-решение для горячих путей (Redis, Aerospike, ClickHouse).
- Сильный кеш и in-memory-структуры кампаний, обновляемые по событиям (Event Sourcing).
- Геораспределённый деплой и anycast/edge-узлы.

5. Какие технологии нужно/стоило бы использовать в проде?
- Go + gRPC/HTTP/2 для внутренних сервисов.
- Postgres/ClickHouse для биллинга и отчётности.
- Kafka / NATS для событий.
- Redis для freq cap и кеша таргетинга.
- Kubernetes, сервис-mesh (mTLS), Prometheus, Grafana, Loki/ELK для логов, OpenTelemetry для трассировки.
- Фичи безопасности: TLS везде, подпись событий, пер-user rate-limit.
